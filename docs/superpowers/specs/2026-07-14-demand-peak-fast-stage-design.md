# Stage5 后置限时需求峰搭切设计

## 1. 目标与结论

在现有 `Stage5 -> LNS` 生产链中插入一个限时需求峰搭切阶段：

`Stage5 -> DemandPeakFastStage -> LNS -> 可选 SPR`

新阶段使用 Stage5 实时结果作为受保护的可行种子，在相同订单需求、总车数和废边上限下重组 message-aware 可执行列，优先减少序号组、奇数组、一车组和小车数组。

本次优化必须同时满足两个目标：

1. 质量不劣于当前 Stage5+LNS，争取进一步减少序号组及坏组。
2. 通过硬时间预算、提前停止和按需跳过控制总耗时，不能复用当前约 60 秒的实验参数直接进入生产链。

需求峰阶段不可行、超时、异常、守恒失败或结果变差时，必须无条件保留原 Stage5 结果，后续继续运行原 LNS。现有正式链路不得因新阶段失败而失败。

## 2. 当前证据

实时 sixian 实验已经证明需求峰方向存在增益：

- Stage5 基线：`56 组 / odd 6 / small 23 / 462 车 / 废边 102240`。
- 需求峰结果：`54 组 / odd 6 / one 2 / small 22 / 462 车 / 废边 102240`。
- MIP 用时约 59 秒，总用时约 65 秒，状态为 `FEASIBLE`。
- 当前 Stage5+LNS 的可比结果可达到 `51 组 / odd 4 / small 16`，总用时约 44 秒。

因此需求峰已经证明“能改善 Stage5 起点”，但尚未证明“能超过 Stage5+LNS”或“能节省总时间”。本设计解决的是生产接入、限时和整体比较问题，不把实验结果描述为已优于现有链路。

## 3. 插入点与数据流

### 3.1 插入点

插入点位于 `InstructionConverter.convertWithDetails(...)` 中：

1. Stage5 生成 `stage5-mip` 指令。
2. 现有候选完成基础质量比较，获得一个可行 `selectedInstructions`。
3. 新阶段从该指令重建 Stage5 可执行列、花型形状和 `(width|message)` 精确需求。
4. 生成需求峰列池并运行限时统一 Set Partition MIP。
5. 只有新结果通过守恒校验且按现有字典序严格更好时，才替换 LNS 的输入。
6. LNS 在选中的更好起点上继续优化。

Phase2 和 greedy 的启用规则保持不变；质量模式下的 SPR 仍在 LNS 之后运行。

### 3.2 新阶段输入

- Stage5 已选指令及其可执行列。
- 当前 group 的原始 `SolverOrderItem`。
- `SolverParameters.totalWidth`。
- Stage5 总车数和总废边，分别作为精确车数和废边上限。
- 请求级运行参数，不使用跨请求共享可变状态。

### 3.3 新阶段输出

阶段结果包含：

- 是否执行及跳过原因。
- 求解状态、列池大小、需求峰、求解耗时和 gap。
- 转换后的 `CuttingInstruction`。
- 阶段前后 `groups / odd / one / small / cars / waste`。

结果名称使用 `stage5-mip+demand-peak`；后续 LNS 改善后沿用现有后缀规则形成 `stage5-mip+demand-peak+lns`。

## 4. 质量与安全规则

### 4.1 守恒门禁

需求峰候选必须同时满足：

1. 每个 `(width|message)` 的生产量与原始需求完全一致。
2. 总车数与 Stage5 完全一致。
3. 总废边不高于 Stage5。
4. 每条指令的花型宽度、工位数量和使用次数合法。
5. 转换后统计值与 MIP 结果一致。

任一条件失败，候选作废并记录原因。

### 4.2 严格拣优顺序

沿用当前业务质量顺序，不新增另一套目标口径：

`超产 -> 总车数 -> 序号组 -> odd -> one -> small -> 花型数 -> 废边`

需求峰候选只有严格优于 Stage5 起点时才进入后续 LNS。相同质量时保留 Stage5，避免无收益地改变稳定结果。

### 4.3 回退规则

下列情况均视为正常回退，不中断整个 group：

- 列池为空或无法覆盖全部需求。
- MIP 返回 `INFEASIBLE`、`NOT_SOLVED` 或异常。
- 达到时间上限但没有合法可行解。
- 结果守恒失败。
- 结果不优于 Stage5。

## 5. 时间控制

### 5.1 默认预算

第一轮默认需求峰预算为每个非平凡 group `10 秒`，通过请求级运行属性配置。小 group 或 Stage5 已经只有 1 组时直接跳过。

### 5.2 提前停止

满足以下任一条件时不再扩展需求峰阶段：

- Stage5 已达到可证明的 1 组下界。
- 可用花型或 message 数不足以形成有效重组。
- 受保护列已经达到当前列池的最佳字典序结果。
- 时间预算耗尽。

### 5.3 性能目标

第一轮验收以整体链路为准：

- sixian 总耗时不高于当前 Stage5+LNS 基线的 `1.15 倍`。
- 如果总耗时增加，必须至少减少 1 个序号组；否则新阶段不得默认启用。
- 如果能在不增加序号组的前提下降低 odd、one 或 small，也记录为质量改善，但不能用它掩盖明显的总耗时回退。

## 6. 实现边界

允许修改：

- `InstructionConverter` 中 Stage5 与 LNS 之间的候选编排。
- `DemandPeakColumnPoolBuilder`、`DemandPeakInitialSolutionSolver` 及必要的转换适配代码。
- 与需求峰阶段直接相关的单元测试、实时实验和 sixian 基准测试。

明确不修改：

- PatternGenerator、ColumnGeneration 和 A 层业务目标。
- 前端、API 字段及默认页面行为。
- Maven/测试框架配置。
- Phase2、LNS 和 SPR 的内部算法。
- 订单、车数、废边、超产等业务口径。

## 7. 方案对比与选择

### 方案 A：Stage5 后限时需求峰，再运行 LNS

优点是需求峰专注改善起点，LNS 继续负责局部修复；可以复用现有回退和质量比较。缺点是增加一个求解阶段，必须严格限制时间。

本次采用该方案。

### 方案 B：需求峰和 LNS 分支并行，最后拣优

质量安全，但两条路径都完整执行，CPU 和总时间开销较大，不符合本次“速度快”的优先目标。

### 方案 C：需求峰直接替换 LNS

链路简单，但当前实时结果仍弱于 LNS，缺少替换证据，本次不采用。

## 8. 验证计划

### 8.1 组件测试

- 需求峰列池选择、受保护列和距离带排序。
- 限时求解可行、不可行和超时回退。
- Stage5 结果转换为可执行列及恢复为指令。
- 质量比较和守恒失败拒绝。
- 1 组、小数据和空列池跳过。

### 8.2 真实数据验证

在相同机器、无其他求解 JVM 干扰的条件下，对 sixian 至少比较：

1. Stage5，不启用 LNS。
2. 当前 Stage5+LNS。
3. Stage5+DemandPeakFastStage+LNS。

每条路线报告：

- 实际执行测试数、成功数、失败数和跳过数。
- groups、odd、one、small。
- cars、waste 和需求守恒。
- Stage5、需求峰、LNS 及总耗时。
- MIP 状态、gap 和列池大小。

如果结果存在随机或时间波动，最终候选至少重复 3 次，并报告最小值、最大值和中位数；不能只选择最好的一次。

## 9. 交付判定

只有满足以下条件才允许把新阶段默认启用：

1. 所有组件测试通过且没有 `0 tests found` 或测试跳过冒充通过。
2. sixian 的需求、车数和废边严格守恒。
3. 最终质量不劣于当前 Stage5+LNS。
4. 总耗时满足性能目标，或者用明确的组数改善补偿小幅耗时增加。
5. 超时、不可行和异常场景都能稳定回退。

若未达到默认启用门槛，代码只能保留为默认关闭的实验阶段，并在结论中明确当前瓶颈和下一步，不得宣称优化方向已经完成。

## 10. 2026-07-14 首轮接入实测

### 10.1 实现结果

- 新阶段已接入 `Stage5 -> DemandPeakFastStage -> LNS`，默认关闭，通过
  `cutting.demandPeak.enabled=true` 显式启用。
- Stage5 的可执行列作为精确可行 warm start；求解、重建或守恒校验失败时保留原结果。
- 默认需求峰预算为 5 秒；新阶段被接受后，普通模式下 LNS 默认缩短为
  `maxIterations=24`、`maxNoImprove=8`，两项均可通过请求级运行属性覆盖。

### 10.2 sixian 三轮对照

| 路线 | 最终 groups/odd/one/small | cars/waste | 总耗时样本 | 中位数 |
|---|---:|---:|---:|---:|
| Stage5+LNS 基线 | `50/4/1/16` | `462/102240` | `49.858s / 54.656s / 54.672s` | `54.656s` |
| Stage5+DemandPeakFastStage+短 LNS | `50/4/1/17` | `462/102240` | `41.740s / 43.421s / 59.486s` | `43.421s` |

需求峰阶段在三轮中都把主 group 的 Stage5 起点从 `55` 降到 `54`，需求、车数和废边保持不变；
端到端中位耗时下降约 `20.6%`。但最终序号组数、奇数组和一车组没有优于基线，small 从 `16`
退化到 `17`。额外把短 LNS 放宽为 `30/10` 后仍为 `50/4/1/17`，因此停止继续堆叠求解时间。

### 10.3 判定

速度方向已得到支持，整体质量门槛尚未通过，因此新阶段保持默认关闭。下一轮应让需求峰候选和目标函数感知
LNS 下游的 small/碎片结构，或补充快速 small 修复，而不是单纯延长 MIP 或 LNS 时间。
