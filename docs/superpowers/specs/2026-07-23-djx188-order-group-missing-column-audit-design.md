# DJX188 订单级组列缺列审计设计

## 1. 背景

订单级组列原型已经验证：

- 自主完整 7717 花型骨架路径可以稳定得到
  `31 组 / 奇数组 1 / 单车组 0 / 169 车 / 36,870 mm 废料`；
- 固定 automatic22 花型支持的诊断消融可以用相同组列主问题得到
  `29/1/0/169/36,870`；
- T42 可以由自动 11 组 incumbent 改善到 `10/1/0`；
- 生产受控 800 骨架池的根 LP 可以下降到约 `17.78`，但整数结果仍为
  31 组。

这证明受限主问题和输出语义能够表达比 31 组更好的结果，但尚未证明
29 组所需的组列究竟在哪个阶段丢失。

当前 oracle 对候选采用单列门禁：

1. 枚举花型骨架；
2. 截断连续车数候选；
3. 每个宽幅保留有限订单配置；
4. 用 beam 合并完整配置；
5. 只保留单列真实 reduced cost 为负的候选；
6. 再经过单花型上限、角色分桶和全局名额选择。

因此现有证据同时兼容四种不同解释：

- 关键车数没有进入候选；
- 关键局部配置或完整配置被截断；
- 关键列 reduced cost 为负，但被入池限额淘汰；
- 关键列单独 reduced cost 非负，只有与其他列联合替换 incumbent 时才有价值。

在区分这四种解释之前直接实现列束定价，仍然可能在错误阶段优化。

## 2. 本轮目标

建立一个只存在于测试侧、可确定性复现的缺列审计器，对 automatic22
诊断方案所选择的 29 条完整组列，在自主完整 7717 路径的候选生成环境中
逐条给出唯一的首要丢失原因。

本轮要回答：

> 已知存在的 29 组精确方案，为什么没有被当前自主定价路径发现并保留？

本轮不追求直接把自主结果从 31 降到 29，也不实现生产列束定价。

## 3. 严格边界

### 3.1 允许

- 修改订单级组列研究原型的测试侧诊断接口；
- 新增缺列审计器和 opt-in DJX188 审计测试；
- 复用现有完整 7717 自主结果、automatic22 诊断结果和 T42 回归；
- 输出确定性分类、数量、签名、分阶段排名和耗时。

### 3.2 禁止

- 修改 `src/main/java`；
- 接入生产求解链；
- 将 automatic22 或人工26花型签名用于自主候选生成、排序或约束；
- 读取人工搭切列作为定价提示；
- 修改或提交用户已有九个未跟踪实验文件；
- 把诊断见证固化成生产白名单；
- 在审计结果出来前实现列束、二跳局部宇宙或完整 branch-and-price。

automatic22 只作为测试判卷见证：

```text
自主求解路径 ────────────────┐
                              ├─ 缺列审计比较
automatic22 独立诊断路径 ────┘
```

两条路径在求解过程中互不读取对方的花型、配置和选择结果。

## 4. 审计输入

一次完整审计固定使用同一 JVM 中生成的两份结果：

### 4.1 自主基线

- DJX188 原始订单；
- 完整 7717 花型骨架宇宙；
- 自动 incumbent；
- 当前默认定价预算与列池上限；
- 最终自主 `Result.pool()` 和 `Result.selectedColumns()`。

完整路径可能在 FEASIBILITY 定价阶段超时，因此审计不得直接把最后一次
可行性对偶当作优化 reduced cost 对偶。审计应对最终自主列池单独运行一次
`Phase.OPTIMIZATION` 的连续受限主问题，取得同一列池下有效的优化对偶。

### 4.2 29组诊断见证

- 相同订单、车数、废料、奇数组和单车组约束；
- automatic22 花型支持；
- 相同组列模型；
- 精确选择出的 29 条完整组列。

见证必须先独立通过逐订单需求、总车数、总废料、奇数组、单车组以及
输出转换语义校验。见证不通过时审计立即失败，不得继续分类。

## 5. 分类语义

每条见证组列按候选管线的先后顺序，只归入第一个命中的类别。

### 5.1 `PRESENT_IN_AUTONOMOUS_POOL`

完整签名已经存在于自主最终列池。

该类别说明列本身没有丢失；若最终未被整数主问题选择，问题属于组合选择，
不属于候选生成。

### 5.2 `PATTERN_NOT_IN_UNIVERSE`

见证花型骨架不在被审计宇宙中。

完整 7717 路径理论上不应出现此类别。出现时应视为宇宙或签名漂移错误，
不得解释为正常剪枝。

### 5.3 `CAR_COUNT_PRUNED`

花型存在，但见证连续车数不在 `candidateCars(pattern)` 的受控候选中。

输出至少包含：

- 见证车数；
- 该花型的完整可行车数上界；
- 实际保留车数；
- 见证车数在未截断候选中的原始排名和截断原因。

### 5.4 `LOCAL_CONFIGURATION_PRUNED`

车数存在，且逐宽幅订单多重集合在完整局部枚举中可行，但至少一个宽幅
没有进入 `maxLocalConfigsPerWidth` 保留集合。

输出每个失败宽幅的：

- 槽位数；
- 目标消息多重集合；
- 完整局部候选数；
- 目标 raw/stable/closure 排名；
- 实际保留上限。

### 5.5 `BEAM_PRUNED`

每个宽幅的目标局部配置均被保留，但合并后的完整订单配置没有进入最终
`beamWidth`。

输出目标完整配置在扩展过程首次丢失的宽幅、当层排名和 beam 上限。

### 5.6 `MATERIALIZED_NONNEGATIVE`

完整组列已经被 materialize，但在自主优化对偶下：

```text
rawReducedCost >= -epsilon
```

它会被当前单列 reduced-cost 门禁正确拒绝。该类别是后续列束定价的直接
候选证据，但单个样本不足以证明列束一定能改善整数 incumbent。

### 5.7 `NEGATIVE_PATTERN_CAP_PRUNED`

单列真实 reduced cost 为负，但在同一花型内部的
`maxColumnsPerPattern` 截断中被淘汰。

### 5.8 `NEGATIVE_GLOBAL_SELECTION_PRUNED`

通过单花型保留后仍为负列，但被角色桶、`maxPerPatternPerIteration` 或
`maxAddedPerIteration` 全局选择淘汰。

输出具体淘汰层、层内排名和上限，不能只报告“排序靠后”。

### 5.9 `GENERATED_IN_DIAGNOSTIC_REPLAY`

在相同对偶、相同配置和相同选择参数下，审计重放确认该列应被返回，
但自主最终列池中不存在。

该类别表示动态工作集淘汰、运行截止时间或跨迭代状态造成的差异。必须继续
报告它是否曾进入历史整数档案；若原型未保留可查询历史，则状态明确标为
`ARCHIVE_PRESENCE_UNKNOWN`，不得推断从未生成。

## 6. 联合替换审计

逐列分类之外，审计还要比较自主31组解与诊断29组解。

### 6.1 规范化差集

按完整组列签名计算：

- `kept`：两个解共有的列；
- `removed`：仅在自主31组解中的列；
- `added`：仅在诊断29组解中的列。

### 6.2 守恒证明

必须证明：

```text
Σ resources(removed) = Σ resources(added)
```

资源向量包含：

- 每个订单需求；
- 总车数；
- 总废料；
- 奇数组数；
- 单车组数。

并计算：

```text
groupDelta = |added| - |removed|
```

预期为 `-2`。若不是 `-2`，说明共有列匹配或见证语义存在漂移，审计失败。

### 6.3 Reduced-cost解释

对 `added` 中每条列记录自主优化对偶下的单列 raw reduced cost，并汇总：

- 负值列数量；
- 非负列数量；
- added 集合 raw reduced cost 总和；
- removed/added 直接目标差；
- 小组 tie-break 差值。

由于 family 行是小于等于约束，family 对偶会随列池变化，集合 reduced
cost 总和只作为当前受限主问题下的解释证据，不能宣称为全局定理。

若满足以下条件：

1. `groupDelta < 0`；
2. 守恒证明通过；
3. `added` 中至少一条列为 `MATERIALIZED_NONNEGATIVE`；

则可以确认“只接收逐列负 reduced cost”会漏掉一个真实整数改进交换，
下一阶段进入有界列束定价设计。

## 7. 组件设计

### 7.1 `OrderGroupMissingColumnAudit`

新增测试侧分析器，负责：

- 接收自主输入、最终列池、优化对偶和29组见证；
- 调用 oracle 的只读解释接口；
- 生成逐列分类；
- 计算31↔29差集与守恒证明；
- 汇总分类计数和下一步判定。

核心输出：

```java
record AuditResult(
        AuditStatus status,
        List<ColumnAudit> columns,
        ExchangeAudit exchange,
        Map<LossStage, Integer> counts,
        Recommendation recommendation,
        long elapsedMs) {}
```

### 7.2 `OrderGroupColumnPricingOracle`

只增加包内可见、无副作用的诊断接口，例如：

```java
CandidateExplanation explain(
        GroupColumn target,
        DualVector rawDual,
        DualVector stableDual,
        ColumnPool pool)
```

要求：

- 复用生产候选路径的同一排序器和同一截断参数；
- 不维护第二套近似分类逻辑；
- 不把 watched signature 注入正常 `price()` 的排序；
- 不改变正常候选返回结果。

### 7.3 `Djx188OrderGroupMissingColumnAuditTest`

新增 opt-in 真实审计测试：

1. 生成自主完整路径；
2. 生成独立29组诊断见证；
3. 对自主最终池重解优化 LP；
4. 执行逐列和联合替换审计；
5. 打印稳定报告；
6. 断言全部29条见证列均有且只有一个分类；
7. 断言交换守恒与 `groupDelta=-2`。

## 8. 确定性与证据口径

- 分类顺序固定；
- 所有签名、宽幅和列按字典序输出；
- 排名采用稳定次序，最终以完整签名打破平局；
- 同一输入重复运行的分类计数、逐列分类和交换签名必须一致；
- 自主生成随机性如导致列池漂移，审计报告记录输入、Options 和自主池哈希；
- 不把一次诊断分类推广为其他数据集的通用规律。

审计状态：

- `COMPLETE`：全部见证列分类唯一，交换守恒通过；
- `WITNESS_INVALID`：29组见证不满足精确语义；
- `AUTONOMOUS_POOL_INVALID`：自主列池不能重解优化 LP；
- `UNCLASSIFIED_COLUMN`：至少一条见证列无法归因；
- `NONDETERMINISTIC`：同一快照重放分类不一致。

## 9. 验证

### 9.1 单元测试

至少覆盖：

1. 已在池中的列归为 `PRESENT_IN_AUTONOMOUS_POOL`；
2. 车数候选截断；
3. 局部配置截断；
4. beam 截断；
5. materialized 但单列 reduced cost 非负；
6. 负 reduced cost 的单花型截断；
7. 负 reduced cost 的全局选择截断；
8. 31↔29模拟交换的完整资源守恒；
9. 非守恒交换被拒绝；
10. 相同快照重复审计得到相同报告。

### 9.2 真实回归

- DJX188 完整自主路径仍精确满足 `31/1/0/169/36,870` 或取得更好结果；
- automatic22 诊断见证仍精确满足 `29/1/0/169/36,870`；
- 29条见证列分类覆盖率为 `100%`；
- T42 仍为 `10/1/0/45/10,820`；
- 输出转换前后语义一致。

### 9.3 耗时

- 单独审计分析目标不超过 5 秒；全宇宙排名重放超过该预算时必须报告
  `AUDIT_TIME_LIMIT`，不能用部分排名给出完整分类；
- 含两次现有求解的完整 opt-in 审计目标不超过 69 秒；
- 分别报告自主求解、见证求解、LP重解和审计耗时；
- 超时不得当作“不存在某类缺列”。

测试报告必须列出实际执行数、成功数、失败数和跳过数。

## 10. 结果驱动的下一步

审计完成后按证据选择唯一后续方向：

### 10.1 车数或配置阶段占主导

若 `CAR_COUNT_PRUNED`、`LOCAL_CONFIGURATION_PRUNED` 或 `BEAM_PRUNED`
覆盖主要 added 列，先修复最早发生的候选截断，不实现列束。

### 10.2 负列选择阶段占主导

若多数 added 列已经是负 reduced cost，只被 pattern/global cap 淘汰，
先修复分桶和受控多样性，不实现列束。

### 10.3 单列门禁被证明有损

若联合替换严格改善且包含 `MATERIALIZED_NONNEGATIVE` 列，则下一阶段设计
“incumbent residual bundle pricing”：

- 从当前精确 incumbent 移出2至4条相关组列；
- 以移出资源向量作为小残量；
- 在残量约束内联合生成并选择更少的替换列；
- 只在整个 bundle 精确守恒且严格减少组数时整体入池；
- 不在7717花型上建立全局支持MIP。

### 10.4 混合结果

若多个阶段均有显著损失，先修复管线中最早的阶段，再重新运行相同审计。
不得同时修改候选枚举和列束接受策略。

- automatic22 仅作为独立诊断见证，不进入自主求解；
- 自主最终列池使用有效优化 LP 对偶，而不是可行性阶段对偶；
- 29条见证列全部得到唯一、可复算的首要丢失原因；

- 审计接口无副作用，不改变正常 oracle 返回；
- 结果只决定下一轮研究方向，不宣称通用生产规律；
- 所有实际测试数量和耗时如实报告；

## 13. 实施结果（2026-07-23）

### 13.1 真实 DJX188 审计

完整7717花型自主路径与独立 automatic22 见证均重新求解，结果为：

| 项目 | 自主路径 | 独立见证 |
|---|---:|---:|
| 序号组 | 31 | 29 |
| 奇数组 | 1 | 1 |
| 单车组 | 0 | 0 |
| 总车数 | 169 | 169 |
| 总废料 | 36,870 | 36,870 |

审计状态为 `COMPLETE`，优化 LP 目标为 `31.001800`。29条见证列全部得到唯一分类：

| 首要阶段 | 数量 |
|---|---:|
| `PRESENT_IN_AUTONOMOUS_POOL` | 1 |
| `LOCAL_CONFIGURATION_PRUNED` | 1 |
| `MATERIALIZED_NONNEGATIVE` | 14 |
| `NEGATIVE_GLOBAL_SELECTION_PRUNED` | 13 |

其中局部配置截断发生在宽幅830：目标配置稳定排序第9，而现行上限为8。
13条列已经具有负 reduced cost，但在有界角色收集或全局列选择中被淘汰。
14条见证列在自主最终优化对偶下单列 reduced cost 非负；完整31↔29交换中共有15条
新增列为非负，其中1条已经存在于自主列池但未被整数主问题选中。

31↔29对称差交换满足逐订单需求、总车数、总废料、奇数组和单车组全部守恒，
`groupDelta=-2`。因此已严格证明：单列 reduced cost 门槛会漏掉一个真实的整数联合改进，
但当前缺口同时还包含局部候选截断和负列选择预算，不能归结为单一原因。

本次独立审计耗时2.743秒，其中优化 LP 重解4毫秒、全宇宙诊断重放2.728秒；
完整 opt-in 测试体耗时49.75秒。审计未触发时间上限。

### 13.2 结论边界

本轮推荐为 `MIXED_EARLIEST_STAGE_FIRST`：

1. 只扩大局部配置上限不足以恢复29组见证，因为仍有13条负列选择损失和14条单列非负列；
2. 只改负列分桶同样不足以覆盖完整联合交换；
3. 非负新增列与严格改善的守恒交换同时存在，构成设计残量列束定价的直接证据；
4. 下一轮必须继续做单变量实验，不得同时修改候选枚举、负列保留和列束接受策略；
5. 本结论只适用于当前DJX188快照，不宣称已经形成通用生产规则。

候选生成逻辑已抽取到独立测试侧组件，审计钩子与正常定价复用同一条候选链路，
不读取人工签名，不改变正常 `price()` 的候选结果。

### 13.3 回归结果

- 快速单元与原型回归：24/24通过，0失败，0错误，0跳过；
- DJX188真实审计：1/1通过，0失败，0错误，0跳过；
- T42跨数据集回归：1/1通过，保持
  `10组/奇数1/单车0/45车/废料10,820`，算法总耗时10.502秒。

最终验证合计26个测试，26个成功，0失败，0错误，0跳过。
