# DJX188 支持候选快照与 Top-3 精确复核设计

## 1. 背景

上一轮结构化局部宇宙实验在一次 JVM 运行内生成了 232 个候选状态、17 个支持结构，并完成了全量 Phase2 与部分精确复核。17 个支持的 Phase2 最优代表最终都被证明无法达到 `groups <= 27, oddGroups = 1, oneGroups = 0`，但该候选快照没有持久化。测试 JVM 退出后，后续快速回归又覆盖了 Surefire 长跑报告，因此原 232 状态无法恢复。

这意味着上一轮的 `17/17` 支持结论和 `24/232` 状态覆盖率只能作为历史参考，不能与下一次生成结果累加。下一阶段必须先把候选快照变成可持久化、可校验、可重放的研究基线，再检查每个支持内部排名第二、第三的系数状态。

## 2. 目标

本轮实现以下能力：

1. 在保持三层局部宇宙和稀疏生成逻辑不变的前提下，重新生成一次候选池；
2. 对全部候选完成 Phase2 后，立即将候选状态、全局支持身份和 Phase2 分数原子落盘；
3. 为文件计算稳定载荷哈希，并将其作为后续所有精确结果的基线身份；
4. 后续 Top-1、Top-2、Top-3、超时重试和完整兼容性核复核只读取该快照，不再调用生成侧；
5. 按支持内部统一排序选取前 3 个系数状态，累计报告支持覆盖和状态覆盖；
6. 使用 `60 秒阈值 -> 180 秒阈值 -> 完整兼容性核` 的分级证据流程；
7. 将精确结果写入与快照哈希绑定的独立旁路文件，不修改不可变候选基线。

## 3. 非目标与范围边界

本轮不做以下事项：

- 不修改生产代码；
- 不修改 WITNESS_DIRECT、NEUTRAL_CLOSURE、TRANSFER_BRIDGE_1_HOP 三层的构造规则；
- 不扩大到二跳桥接；
- 不修改稀疏 MIP 目标函数；
- 不提高或重新分配三层生成预算；
- 不把上一轮 232/17 的结果合并进新快照；
- 不声称相同种子和配置必然生成相同状态集合；
- 不因 Phase2 未发现 27 组而宣称精确不可行；
- 不因精确求解超时而将状态记为不可行。

所有新增类、测试、资源和输出均位于研究测试侧。

## 4. 核心决策

### 4.1 新建专用候选快照格式

现有 `SolverExperimentSnapshot` 保存的是完整订单配置列和排产结果，不包含稀疏候选状态、支持身份、来源层和 Phase2 分数。它不能直接承担本轮重放语义。

新增独立格式：

```text
support-candidate-snapshot-v1
```

实现沿用现有快照组件的 UTF-8、确定性排序和临时文件原子替换原则，但不复用其数据模型。

### 4.2 候选快照不可变，精确证据独立保存

候选基线文件：

```text
src/test/resources/research-baselines/
  djx188-support-candidate-snapshot-v1.tsv
```

精确结果旁路文件：

```text
src/test/resources/research-baselines/
  djx188-support-candidate-exact-results-v1-<payloadSha256-prefix>.tsv
```

候选快照一旦建立，Top-N 评价不得修改它。精确旁路文件名和文件头必须同时绑定候选快照载荷 SHA-256；哈希不一致时拒绝读取或合并。建立新基线时不得覆盖、删除或改写旧哈希对应的精确旁路文件。

### 4.3 不自动重新生成

实验提供显式模式：

- `CREATE`：运行三层生成和全量 Phase2，创建新快照；目标文件已存在时默认失败；
- `REPLACE`：仅在明确要求建立新统一基线时允许替换快照；旧哈希对应的精确旁路文件保留为历史证据，但不会被新快照读取；
- `REPLAY`：只读现有快照并运行 Top-N/精确流程；文件缺失或校验失败时直接失败，不回退到生成；
- `VERIFY`：只回读、校验并报告快照，不运行 Phase2 或精确求解。

Top-N 日常入口默认使用 `REPLAY`。

## 5. 快照元数据

### 5.1 基本身份

快照头部至少记录：

- `format=support-candidate-snapshot-v1`；
- `dataset=DJX188`；
- `createdAtUtc`；
- `producerGitHead`；
- `producerWorktreeDirty`；
- `producerRelevantSourceSha256`；
- Java 版本、OR-Tools 版本、求解器名称；
- `stateCount`；
- `supportCount`；
- Phase2 状态计数；
- `payloadSha256`。

`producerRelevantSourceSha256`由本轮候选生成、支持身份、Phase2 评价所依赖的研究侧源码内容按规范路径排序后计算，用于识别“提交号相同但相关源码未提交”的运行。`producerWorktreeDirty`只记录事实，不因为存在与本实验无关的工作树改动而拒绝创建。

`payloadSha256`基于会影响候选语义的规范化配置元数据和全部状态载荷计算。`createdAtUtc`、`producerGitHead`、`producerWorktreeDirty`等易变生产信息以及哈希字段自身不参与计算，因此相同规范载荷可得到相同身份哈希。

### 5.2 随机性与线程

当前稀疏 MIP 已明确配置：

- `parallel/maxnthreads=1`；
- `randomization/randomseedshift=0`；
- `randomization/permutationseed=0`；
- `randomization/lpseed=0`。

快照必须原样记录这四项。实现不得为了快照功能改变这些参数。

### 5.3 生成预算与容量

至少记录：

- `sparseTotalMs=20000`；
- `sparseMasterMs=20000`；
- `sparseSupportMs=15000`；
- `sparseNodeLimit=200000`；
- `sparseMaxSupports=200`；
- `sparseMaxCoefficients=2000`；
- `sparseMaxStates=500`；
- 局部宇宙构造预算与上限；
- 总车数 169、总废料 36870、总宽度等业务不变量。

时间预算记录的是每层使用的同一组配置，不表示三层共享一个 20 秒总预算。

### 5.4 结构哈希

生成配置规范化为按键排序的 UTF-8 `key=value` 序列，计算：

```text
generationConfigSha256
```

哈希输入至少包含：

- DJX188 需求向量哈希；
- automatic22 基线解哈希；
- 7717 完整花型宇宙签名哈希；
- 三层各自的花型签名集合哈希；
- 三层构造规则名称；
- 稀疏生成 Options 全字段；
- preferred pattern/width 集合哈希；
- SCIP 单线程和三个随机种子参数。

同时分别记录：

- `witnessDirectUniverseSha256`；
- `neutralClosureUniverseSha256`；
- `transferBridgeUniverseSha256`。

相同 `generationConfigSha256` 只说明生成条件一致。由于求解受墙钟时间截断影响，实际状态集合仍可能不同；实际可比性必须以 `payloadSha256` 为准。

## 6. 每个候选状态的载荷

每条状态记录至少包含：

- `stateSignature`：完整花型使用次数，可重建 `Map<PatternCandidate, Integer>`；
- `supportIdentity`：忽略系数绝对值的全局带符号支持身份；
- 来源层集合；
- 对应主 MIP 目标值集合；
- Phase2 状态；
- Phase2 组数；
- Phase2 奇数组数；
- Phase2 单车组数；
- Phase2 耗时；
- 是否满足 Phase2 目标形态。

状态按 `stateSignature` 升序写入。含分隔符的签名使用 URL-safe Base64 无填充编码，避免制表符或未来格式扩展破坏解析。

快照不依赖 Java 对象序列化，防止类结构变化导致历史文件无法读取。

## 7. 原子写入与完整性

### 7.1 写入流程

1. 在内存中生成规范化元数据和状态行；
2. 计算 `payloadSha256`；
3. 写入同目录临时文件；
4. 重新读取临时文件并完成全部校验；
5. 使用 `ATOMIC_MOVE + REPLACE_EXISTING` 替换目标；
6. 文件系统不支持原子移动时，使用已有快照组件相同的安全替换降级路径。

### 7.2 覆盖保护

`CREATE`遇到已有目标时失败。`REPLACE`必须由独立系统属性显式开启，并在日志中打印旧、新载荷哈希。不得因读取失败、格式不兼容或哈希错误自动覆盖文件。

`REPLACE`只替换候选基线文件。由于精确旁路文件名包含快照哈希，新基线会自然使用新的旁路文件；旧旁路文件原样保留，不做隐式删除、重命名或覆盖。

### 7.3 回读校验

读取时至少验证：

- 格式版本；
- 载荷哈希；
- 状态数和支持数；
- 状态签名唯一；
- 每个状态只对应一个支持身份；
- 从状态签名重建后的签名完全一致；
- 每个解总车数为 169；
- 每个解逐宽幅生产量与 DJX188 需求一致；
- Phase2 字段合法且状态计数与头部一致；
- 三层配置哈希与文件元数据内部一致。

`REPLAY`可额外比较当前代码计算出的 DJX188 需求哈希和基线解哈希；不一致时拒绝评价。

## 8. 快照建立与重放数据流

### 8.1 CREATE/REPLACE

```text
加载 DJX188
  -> 构造 7717 完整宇宙
  -> 构造三层局部宇宙
  -> 每层按原配置运行稀疏 MIP
  -> 单次内存冻结候选
  -> 全量 Phase2
  -> 构造快照归档
  -> 原子写入
  -> 立即回读校验
  -> 后续 Top-N 使用回读对象
```

Top-N 不得继续使用写入前的内存对象，以确保实际验证的是可重放文件，而不是相似但未序列化的数据。

### 8.2 REPLAY

```text
读取快照
  -> 校验哈希和业务不变量
  -> 重建候选解与 Phase2 分数
  -> 支持内排名
  -> 读取/合并精确结果旁路
  -> 仅求解缺失状态
```

报告必须打印：

```text
snapshotSource=REPLAY
generationInvoked=false
snapshotPayloadSha256=...
```

## 9. 支持内 Top-1/2/3 排名

### 9.1 排名语义

每个支持内部沿用已验证的 Phase2 排名：

1. `targetShapeFeasible=true` 优先；
2. 其他 Phase2 `FEASIBLE` 次之；
3. 无解、非法或错误状态最后；
4. 同层级按 Phase2 组数升序；
5. 最后按 `stateSignature` 稳定排序。

不得用主 MIP 的 `-3300` 等目标值替代该排序，也不得给单个花型固化兼容性罚分。

### 9.2 累计深度

定义：

- `depth=1`：每个支持的第 1 名；
- `depth=2`：第 1、2 名累计集合；
- `depth=3`：第 1、2、3 名累计集合。

支持不足 N 个状态时只取实际存在的状态，并单独报告：

- 具备第 N 名的支持数；
- depth N 新增状态数；
- depth N 累计唯一状态数；
- 累计状态覆盖率 `checkedUniqueStates / snapshotStateCount`。

状态身份仍以 `stateSignature` 去重，支持身份不包含系数绝对值。

### 9.3 排序信号诊断

“排名第二、第三”由 Phase2 排名定义，因此它们通常不会拥有比同支持第一名更好的 Phase2 排名。真正需要检验的是：

- Phase2 排名更后的状态是否反而拥有更好的精确组数下界或可行形态；
- rank 2/3 是否出现 rank 1 未出现的精确 `<=27/1/0` 可行解；
- 非目标形态但 Phase2 组数更低的状态，是否经精确分配后恢复目标形态；
- Phase2 排名与精确结果之间是否存在反序。

报告仍统计 rank 2/3 的 Phase2 组数分布，以及是否出现低于当前全局 Phase2 最好值的状态，但不得把这一统计误写成精确结论。

## 10. 精确分级策略

每个尚无旁路结果的状态依次执行：

### 10.1 第一阶段：60 秒阈值 MIP

目标固定为：

```text
groups <= 27
oddGroups = 1
oneGroups = 0
```

- `FEASIBLE`：已证明目标存在；随后运行完整分析确认精确组数和形态；
- `INFEASIBLE`：已证明该状态不能达到目标；停止；
- `UNKNOWN`：进入 180 秒重试。

### 10.2 第二阶段：180 秒阈值重试

使用相同模型和目标，仅扩大时间预算：

- `FEASIBLE`或`INFEASIBLE`按上一阶段处理；
- `UNKNOWN`进入完整兼容性核。

### 10.3 第三阶段：完整兼容性核

默认预算：

- 最小组数阶段 300 秒；
- 奇数/单车形态阶段 60 秒。

以下证据可判定“不存在 27 组目标解”：

- 完整分析证明最小组数大于 27；或
- `provenGroupLowerBound > 27`。

以下证据可判定“找到目标解”：

- 阈值模型返回满足 `<=27/1/0` 的 FEASIBLE；完整分析用于补充最优性，不撤销已存在的可行见证。

若完整分析既没有给出目标可行见证，也没有证明组数下界大于 27，则最终状态仍为 `UNKNOWN`。

## 11. 精确结果旁路文件

格式：

```text
support-candidate-exact-results-v1
```

头部记录：

- 候选快照 `payloadSha256`；
- 精确模型配置哈希；
- 结果条数；
- 结果载荷哈希。

旁路文件名使用候选快照完整哈希的稳定前缀；读取时仍必须核验文件头中的完整哈希，不能只信任文件名。若不同完整哈希发生前缀碰撞，则拒绝使用该路径并要求扩大文件名前缀长度。

每条结果记录：

- `stateSignature`；
- 支持身份；
- 支持内 rank；
- 60 秒阈值状态、节点和耗时；
- 180 秒阈值状态、节点和耗时；
- 完整分析状态、最小组数、证明下界、奇数、单车、节点和耗时；
- 最终证据分类：`TARGET_FEASIBLE / PROVEN_NOT_TARGET / UNKNOWN`。

旁路文件采用读取、合并、规范化排序、原子替换的方式更新。只有候选快照哈希完全一致时才允许复用已有结果。

## 12. 报告指标

### 12.1 快照身份

- 快照路径；
- 模式；
- payload SHA-256；
- generation config SHA-256；
- 三层宇宙哈希；
- 状态数、支持数；
- 是否调用生成侧和 Phase2。

### 12.2 Top-N 覆盖

按 depth 1、2、3 分别报告：

- 支持总数；
- 具备该 rank 的支持数；
- 新增状态数；
- 累计唯一状态数；
- 累计状态覆盖率；
- 精确确定数、未知数、目标可行数；
- 不得仅报告支持覆盖而省略状态覆盖。

### 12.3 排名相关性

- 每个 rank 的 Phase2 组数分布；
- 每个 rank 的精确最小组数/下界分布；
- rank 2/3 相对 rank 1 的精确改善数；
- Phase2 非目标形态经精确求解恢复目标形态的数量；
- 主 MIP 目标值与 Phase2/精确结果的交叉分布。

### 12.4 历史边界

报告必须明确：

- 旧 232/17 快照不可恢复；
- 新文件是新的统一基线；
- 旧 `24/232` 覆盖率不能与新分母累加；
- 只有新快照内的 depth 1/2/3 结果可以累计。

## 13. 组件划分

建议新增：

### 13.1 `SupportCandidateSnapshotArchive`

职责：

- 定义 v1 数据模型；
- 规范化编码和解码；
- 计算配置与载荷哈希；
- 原子写入；
- 回读完整性和业务不变量校验；
- 不调用任何求解器。

### 13.2 `SupportTopNExactEvaluator`

职责：

- 从快照按支持建立稳定排名；
- 构造 depth 1/2/3 累计计划；
- 管理三阶段精确求解流程；
- 读取和原子更新精确旁路；
- 汇总覆盖和相关性指标。

### 13.3 `Djx188SupportCandidateSnapshotExperimentTest`

职责：

- 在 CREATE/REPLACE 模式下复用现有三层构造和稀疏生成链路；
- 在 REPLAY/VERIFY 模式下保证不调用生成侧；
- 运行真实 DJX188 Top-N 实验；
- 输出清晰的证据边界。

现有 `SupportBucketedCandidateEvaluator`继续保留候选冻结和 Phase2 排名语义；Top-N 逻辑优先复用其评分比较规则，避免产生两套排序。

## 14. 测试设计

### 14.1 快照格式单元测试

- 小型候选池写入后可完整回读；
- 状态、支持、来源层、主目标和 Phase2 字段逐项一致；
- 写入顺序不同时产生相同规范载荷哈希；
- 创建时间、提交号或无关工作树状态不同时，相同规范载荷仍产生相同哈希；
- 修改任一状态行后哈希校验失败；
- 车数或需求不一致时读取失败；
- CREATE 不覆盖已有文件；
- REPLACE 显式开启后才允许替换。
- REPLACE 后旧哈希旁路文件保持不变，新快照使用独立旁路文件。

### 14.2 Top-N 单元测试

- 每个支持按统一 Phase2 规则稳定排序；
- depth 1/2/3 累计集合正确；
- 支持状态数不足 N 时正确截断；
- 状态覆盖分母固定为快照状态数；
- 同一状态不会在多个深度重复计数；
- rank 2/3 的精确反序可被正确统计。

### 14.3 精确分级状态机测试

使用可注入的假求解结果验证：

- 60 秒 INFEASIBLE 后不再重试；
- 60 秒 UNKNOWN 后进入 180 秒；
- 180 秒 UNKNOWN 后进入完整分析；
- 完整下界大于 27 时记为 PROVEN_NOT_TARGET；
- 全部阶段证据不足时保持 UNKNOWN；
- 已有旁路结果时不重复调用求解器。

### 14.4 真实创建与重放

CREATE 长实验必须证明：

- 三层生成配置和当前锚点一致；
- 全量 Phase2 数等于快照状态数；
- 文件写入后回读对象与写入前规范内容一致；
- 新基线的状态数和支持数如实报告，不要求等于历史 232/17。

REPLAY 长实验必须证明：

- `generationInvoked=false`；
- 使用同一个 payload SHA-256；
- 两次重放的 Top-N 计划状态签名完全一致；
- 精确旁路仅补充缺失状态，不改变候选分母。

## 15. 验收标准

实现完成必须同时满足：

1. 生产代码零改动；
2. 三层构造和 20 秒/层稀疏生成配置未改变；
3. 随机种子和单线程参数被真实记录；
4. 生成配置哈希与实际快照载荷哈希明确分离；
5. 候选快照原子写入并立即回读校验；
6. REPLAY 缺文件或校验失败时不得自动生成；
7. 新基线建立后，Top-1/2/3只读取该文件；
8. 精确结果旁路与快照哈希强绑定；
9. Top-1/2/3均报告状态覆盖率和支持覆盖率；
10. 使用60秒、180秒、完整核三级证据流程；
11. UNKNOWN始终保持未知；
12. 不继承或累加旧232/17快照的覆盖数字；
13. 单元测试、相关回归、真实CREATE和REPLAY测试报告实际执行数；
14. 新基线文件和精确结果文件纳入提交，成为可复核研究证据。

## 16. 结论边界

Top-3检查完成后允许的结论只有：

- 若任一状态获得`TARGET_FEASIBLE`：证明固定新快照中存在27组目标解，并定位其支持与rank；
- 若所有Top-3状态均为`PROVEN_NOT_TARGET`：证明每个支持前三个Phase2状态均不能达到目标，但不能证明快照剩余状态或完整局部宇宙不存在目标解；
- 若仍有UNKNOWN：结论保持不完整，必须报告未知状态数量和覆盖率；
- 只有新快照全部状态完成确定精确评价且全部不可行，才能宣称该固定候选池不存在27组；
- 只有在固定快照评价充分后，才进入生成预算平台实验或二跳桥接设计。
