# DJX188 订单级组列生成原型设计

## 1. 背景与路线转向

当前生产求解链把决策拆成两层：

1. 上游按宽幅需求选择切割花型及使用次数；
2. 下游 Stage5、Phase2、LNS 和 SPR 再把逐订单需求分配到已选花型，并尝试减少序号组、奇数组和单车组。

既有实验已经证明：

- 人工 26 花型交给当前 A 层重新计算使用次数，仍能稳定得到
  `26 组 / 1 个奇数组 / 0 个单车组 / 169 车 / 36,870 mm 废料 / 0 超产`；
- 当前自动花型即使在车数、废料和超产上与人工打平，也可能得到明显更多的序号组；
- 订单兼容性是“花型集合、订单槽位配置和连续运行车数”的联合属性，不能化成可相加的单花型静态罚分；
- 当前研究侧生产中性移动和局部宇宙搜索可以解释差距，但生成阶段本身已达到分钟级，不适合作为在线生产主流程。

因此本轮不再继续扩大局部支持搜索，而是把列从“裸花型”提升为“订单级序号组”：

```text
组列 = 切割花型骨架 + 完整订单槽位配置 + 连续运行车数
```

一条组列在生成时就能确定：

- 覆盖哪些 `width + messageText` 订单以及覆盖数量；
- 贡献多少车；
- 贡献多少废料；
- 是否为奇数组；
- 是否为单车组或小组；
- 在最终结果中贡献一个序号组。

## 2. 架构定位

首版实现为：

```text
根节点订单级 LP 列生成
  -> 受限整数主问题（restricted integer master）
  -> 直接还原订单配置块
  -> 现有离线 kernel 与最终序号组口径验收
```

首版不是完整 branch-and-price。

完整 branch-and-price 需要在每个分支节点重新运行定价，并使用不会破坏定价结构的分支规则。当前项目基于 OR-Tools `MPSolver`，没有现成的节点级自定义定价接入点。本轮只验证“决策粒度前移后，根节点生成的有限组列能否得到更好的整数解”，不宣称全局最优。

## 3. 方案比较与选型

### 3.1 既有 7717 花型作为有限定价 oracle（采用）

每轮扫描完整花型宇宙，但不把完整宇宙加入主问题。对每个花型骨架只构造受控数量的订单配置和连续车数候选，计算真实 reduced cost 后，按角色分桶加入少量负 reduced-cost 组列。

优点：

- 隔离“组列模型是否正确”和“动态规划花型生成是否正确”两个变量；
- 7717 个骨架的只读扫描远轻于把 7717 列或其组合支持放入 MIP；
- 可以复用 `CompletePatternEnumerator`、订单 fixture 和已验证 kernel；
- 首轮失败时能够判断问题在组列模型、订单配置构造还是候选车数，而不是同时怀疑 DP。

缺点：

- 定价 oracle 对订单配置仍是受控生成，不是完整配置空间穷尽；
- 即使没有找到负 reduced-cost 列，也不能宣称完整 LP 已最优。

### 3.2 直接开发联合动态规划定价

直接在宽幅容量、订单槽位和连续车数维度求最佳组列。最终在线形态更紧凑，但首轮会同时引入新的主问题和新的 DP 定价器，归因困难。本轮不采用。

### 3.3 完整 branch-and-price

理论完整性最高，但需要节点级定价、兼容分支规则和更复杂的全局界管理，不适合作为当前最小验证步骤。本轮不采用。

## 4. 目标与成功标准

### 4.1 功能目标

建立一个完全不读取人工花型签名的研究原型：

1. 以逐订单需求作为主问题约束；
2. 动态生成包含花型、订单配置和车数的组列；
3. 将主问题列池控制在几百列；
4. 用受限整数主问题直接选择序号组；
5. 输出能够还原成现有 `AssignmentBlock` 和切割指令的数据；
6. 用人工基准只做结果验收，不参与列生成或排序。

### 4.2 DJX188 第一阶段验收

硬约束：

- 总车数 `169`；
- 总废料 `36,870 mm`；
- 超产 `0`；
- 逐 `width + messageText` 精确满足需求；
- 奇数组 `1`；
- 单车组 `0`。

质量目标：

- 首个架构验收目标为序号组数 `<= 29`；
- 稳定达到 29 后继续追求 `27`，最终目标为人工基准 `26`。

性能目标：

- 花型 oracle 扫描与组列定价总耗时 `5～10 秒`；
- 完整研究流程不超过当前生产质量解约 `69 秒`；
- 主问题保留列数默认不超过 `500`。

未达到上述目标时必须输出真实结果和瓶颈阶段，不得通过读取人工列、放宽超产或隐藏超时来满足断言。

### 4.3 T42 交叉验收

T42 用于防止规则过拟合 DJX188：

- 精确满足订单需求；
- 保持已验证总车数和废料口径；
- 奇数组 `1`、单车组 `0`；
- 使用 T42 自身需求动态枚举完整花型骨架，不复用 DJX188 的 7717 花型宇宙；
- 不读取 T42 已知花型签名；
- 报告组数、列数、迭代数和分阶段耗时。

## 5. 范围与非目标

本轮允许：

- 新增独立设计文档；
- 新增 `src/test/java` 下的组列原型、单元测试和 opt-in 真实实验；

  `AssignmentMIPSolver.AssignmentBlock` 和现有 fixture；

- 修改当前 `Phase2SequenceGroupSolver`、Stage5、LNS、SPR 或默认参数；

  `LegacyOrderPatternSelectionSolver.java` 改动；

## 6. 核心数据模型

### 6.1 订单键

```java
record DemandKey(int width, String messageText)
```

同宽幅不同订单必须保持独立约束，不再只按宽幅聚合。

### 6.2 完整槽位配置

```java
Map<Integer, List<String>> stationConfig
```

每个宽幅对应一个消息编号多重集合，元素个数必须等于花型在该宽幅上的槽位数。签名生成时：

- 宽幅升序；
- 同宽幅消息编号排序；
- 多重集合保留重复次数；
- 不把槽位排列差异误当成不同配置。

### 6.3 组列

```java
record GroupColumn(
        PatternCandidate pattern,
        Map<Integer, List<String>> stationConfig,
        int cars,
        Map<DemandKey, Integer> coverage,
        int totalWaste,
        boolean odd,
        boolean oneCar,
        boolean small,
        ColumnRole role,
        String signature)
```

其中：

```text
coverage[order] = 该订单在完整槽位配置中的槽位数 × cars
totalWaste      = pattern.realWaste × cars
odd             = cars % 2 == 1
oneCar          = cars == 1
small           = cars <= SequenceGroupPostProcessor.SMALL_CAR_MAX_CARS（当前为 5）
```

组列变量为二元变量。同一花型、同一订单配置若被选择两次，在当前允许全局重排的业务语义下应合并为更长连续车数，因此不允许用两个完全相同的组列表示两个本可合并的序号组。

该假设不覆盖未来可能引入的固定交期顺序或禁止跨区间合并约束。

### 6.4 列角色

至少区分：

- `EVEN_CORE`：偶数车主干组；
- `ODD_REQUIRED`：承担总车数奇偶所必需的奇数组；
- `RESIDUAL_CLOSURE`：关闭一个或多个订单残量；
- `SMALL_FALLBACK`：小车数组兜底；
- `ONE_CAR_FALLBACK`：仅在显式允许单车时使用。

角色只用于候选多样性和名额分配，不改变真实 reduced cost，不成为永久静态罚分。

## 7. 受限主问题

### 7.1 LP 变量

对当前列池中的每条组列 `g` 定义：

```text
0 <= z[g] <= 1
```

根节点 LP 使用连续变量以获得对偶价格。最终受限整数主问题把相同变量改为二元变量。

### 7.2 约束

DJX188 原型固定已独立验证的生产主指标，以隔离序号组结构：

```text
每个订单 i：
    Σ coverage[i,g] * z[g] = demand[i]

总车数：
    Σ cars[g] * z[g] = 169

总废料：
    Σ totalWaste[g] * z[g] = 36870

奇数组：
    Σ odd[g] * z[g] = 1

单车组：
    Σ oneCar[g] * z[g] = 0
```

生产泛化阶段再把车数、废料和形态目标恢复为词典序优化。本轮固定它们，目的是只检验能否在相同生产结果下减少组数。

### 7.3 初始可行性

初始主问题不得读取人工方案。采用两阶段人工变量机制：

1. 为订单、车数、废料和形态等式加入正负人工变量；
2. 第一阶段最小化人工变量总量；
3. 定价器使用该阶段对偶价格生成能够消除人工变量的组列；
4. 人工变量全部为零后固定为零，进入组数优化；
5. 最终整数解若仍使用任何人工变量，结果记为 `INFEASIBLE_RMP`，不得输出为有效方案。

同时允许加入不依赖人工签名的确定性纯订单种子列，降低初始退化，但种子列不享有特殊目标优势。

### 7.4 目标

在硬约束全部满足后：

1. 最小化活动组列数；
2. 固定最小组数后最小化小组数；
3. 固定前两项后最小化废料数值误差和稳定签名，仅作为确定性 tie-breaker。

奇数组和单车组在 DJX188/T42 首轮中作为目标形态硬约束，不与组数用脆弱的大权重混合。

## 8. 定价 oracle

### 8.1 输入

- 当前 LP 的逐订单对偶价格；
- 总车数、废料、奇数组和单车组约束的对偶价格；
- 7717 个完整花型骨架；
- 逐订单剩余需求与固定业务目标；
- 当前列池签名集合；
- 时间、候选数和每角色新增名额。

### 8.2 连续车数候选

不枚举所有 `1..maxCars`。对每个配置构造以下确定性候选集合：

- 每个涉及订单的 `demand / slotMultiplicity` 精确闭合点；
- 精确闭合点的合法 `±1` 邻域；
- 不超过上界的最近偶数；
- 当前已验证常见批次角色 `10/8/6/4/3/2`；
- 配置可行最大车数；
- 仅在显式允许单车兜底时加入 `1`。

候选集合去重、升序规范化，并逐项校验任何订单覆盖不得超过需求。

### 8.3 订单配置构造

对每个花型骨架和候选车数：

1. 按宽幅独立读取可用订单；
2. 使用订单对偶收益、是否闭合残量和槽位容量构造每个宽幅的前若干个消息多重集合；
3. 通过固定宽度的 beam search 合并为完整跨宽幅配置；
4. beam 内必须保留纯订单、混合余数和残量闭合三类配置；
5. 不做全部订单配置笛卡尔积；
6. 不使用人工配置签名。

首版默认：

- 每宽幅最多保留 `4` 个局部配置；
- 跨宽幅 beam 宽度 `8`；
- 每个花型骨架最多产生 `16` 个待定价组列；
- 所有上限作为显式 `Options` 字段进入诊断输出。

### 8.4 Reduced cost

真实 reduced cost 必须使用当前未平滑的 LP 对偶价格重新计算：

```text
rc(g)
  = groupCost(g)
  - Σ demandDual[i] * coverage[i,g]
  - carsDual * cars[g]
  - wasteDual * totalWaste[g]
  - oddDual * odd[g]
  - oneCarDual * oneCar[g]
```

对偶平滑只用于 oracle 内部候选排序：

```text
stableDual = alpha * currentDual + (1 - alpha) * previousStableDual
```

默认 `alpha=0.7`。任何候选加入主问题前必须用 `currentDual` 复算，并满足
`rc < -epsilon`。

### 8.5 分桶加入

每轮不按单一 reduced cost 排名前缀加入。按列角色分桶：

- 每个角色先取最优列；
- 再按真实 reduced cost 补足全局名额；
- 同一花型骨架默认每轮最多加入两列；
- 默认每轮新增上限 `20`；
- 列池默认上限 `500`。

这样避免同一花型配置的多个相邻车数挤占全部新增名额。

## 9. 去重、支配与退化控制

### 9.1 去重

组列签名包含：

```text
pattern.signature
+ canonical stationConfig
+ cars
```

相同签名只能进入列池一次。

### 9.2 安全支配

只有下列资源向量完全一致时才允许删除弱列：

```text
逐订单 coverage
总车数
总废料
odd
oneCar
small
```

此时保留目标成本更低或稳定签名字典序更小的列。

同一花型和配置的不同车数通常具有不同覆盖向量，不得仅因车数相近或 reduced cost 较差就永久判定为支配。

### 9.3 退化诊断

每次真实实验至少报告：

- oracle 扫描花型数；
- 构造配置数、车数候选数和总定价候选数；
- 重复签名数；
- 安全支配淘汰数；
- 真实负 reduced-cost 列数；
- 各角色加入数；
- 相同覆盖向量比例；
- LP 迭代目标变化；
- 对偶向量相邻迭代 L1 变化；
- 连续无改善迭代数；
- 最终 LP 与受限整数解差距；
- 定价、LP、整数化和验收耗时。

## 10. 终止语义

列生成在以下任一条件下终止：

- 连续三轮没有找到真实负 reduced-cost 新列；
- 达到列池上限；
- 达到定价总时间上限；
- LP 非正常结束；
- 人工变量无法继续下降。

终止状态必须区分：

- `NO_NEGATIVE_COLUMN_FOUND`；
- `COLUMN_CAP_REACHED`；
- `TIME_LIMIT`；
- `MASTER_FAILED`；
- `ARTIFICIAL_SLACK_REMAINS`；
- `INTEGER_MASTER_FEASIBLE`；
- `INTEGER_MASTER_INFEASIBLE`。

由于订单配置和车数候选是受控生成，即使扫描了全部 7717 个花型骨架，
`NO_NEGATIVE_COLUMN_FOUND` 也只表示“当前 oracle 范围内未找到”，不得表述为完整 LP 最优。

## 11. 结果还原与验收

每个被选中的组列直接转换为：

```java
AssignmentMIPSolver.AssignmentBlock.fromStationConfig(
        groupColumn.stationConfig(),
        groupColumn.cars())
```

并聚合得到：

- `Map<PatternCandidate, Integer>` 花型使用次数；
- `Map<PatternCandidate, List<AssignmentBlock>>` 订单配置块；
- 最终指令和序号组指标。

验收顺序：

1. 逐订单重新汇总，确认精确满足且无超产；
2. 重新计算总车数和废料；
3. 直接统计活动组列、奇数组、单车组和小组；
4. 通过现有输出转换链验证最终展示口径；
5. 对决赛结果调用 `OrderCompatibilityKernelAnalyzer`，记录给定花型使用次数下的精确最小组数和形态；若精确核得到更少组，明确归因为当前组列池仍有缺列，不把它误报成语义错误；
6. 与人工基准只比较指标，不读取人工列。

若输出转换后的序号组数与活动组列数不一致，必须打印被合并或被拆分的完整配置签名，并将结果标记为 `SEMANTIC_MISMATCH`。

## 13. 测试设计

### 13.1 单元测试

至少覆盖：

1. 同一槽位多重集合的不同输入顺序生成相同签名；
2. 同一花型和配置的不同车数生成不同签名；
3. 只有完整资源向量相同时才允许支配删除；
4. 平滑对偶只影响预排序，加入前使用原始对偶复算；
5. `oneCar=0` 时 oracle 不生成一车列；
6. 订单覆盖、总车数、废料、奇数组和单车组等式同时成立；
7. 人工变量未归零时不得输出有效整数方案；
8. 使用次数奇偶与配置组奇偶不能混淆；
9. 分桶后不同角色不会被同一花型骨架垄断；
10. 相同输入和固定种子得到相同列签名与最终结果。

## 15. 实现后修订与实验证据

### 15.1 LP 可行不等于整数 RMP 可行

实现验证出一个原设计未显式写出的边界：人工变量归零只证明根 LP
在当前组列上连续可行，不能保证同一列池存在整数可行组合。

因此研究原型补充了一个不读取人工签名的自动 incumbent：

1. 在生产生成器给出的受控花型骨架池上，求解精确宽幅产需、车数、
   废料、使用次数奇偶和激活联动；
2. 禁止花型只使用一次；
3. 只在该自动支持内运行相同的订单级组列模型；
4. 将得到的完整订单组列作为最终整数主问题的可行基线；
5. 全宇宙定价池与 incumbent 分离，定价未收敛时仍可如实返回已证明
   的可行方案。

该机制不是人工 warm start，也不是生产最终架构；它是根节点原型在
没有完整 branch-and-price 时保证整数可行性的研究侧 primal heuristic。

### 15.2 动态工作集与整数档案必须分离

500 列上限被实现为 LP 动态工作集，而不是永久删除证明：

- 工作集达到上限后保留 LP 活动列和本轮新列；
- 被移出的列允许后续重新生成；
- 历史生成列进入独立、有界的整数档案；
- 最终只对整数档案做一次精确复核；
- 工作集淘汰、定价穷尽和整数评价穷尽分别报告，不得混用。

这项修订来自真实反例：只保留当前 LP 工作集时，LP 可行但整数主问题
可能不可行；加入可行 incumbent 后可以稳定返回方案，但历史列是否能
改善 incumbent 仍需单独评价。

### 15.3 family 行必须从首列开始存在

同一花型与订单配置的不同车数变体受 `family <= 1` 约束。若只在第二个
变体出现后才动态创建该行，定价前后的主问题行集合不同，入池前计算的
负 reduced cost 不再具有预测意义。

实现已改为 family 首列出现时即创建稳定行，并新增“负 reduced cost
确实降低受限主问题目标”的独立单元测试。该修复不改变整数可行域。

### 15.4 当前真实结果

截至本轮实现：

- DJX188 完整 7717 骨架路径：
  - 自动 incumbent 为 `31 组 / 奇数 1 / 单车 0`；
  - 精确满足 `169 车 / 36,870 mm 废料 / 0 超产`；
  - 10 秒全宇宙定价未把整数结果降到 29；
  - 输出转换前后指标一致；
  - 两次完整复跑总算法耗时分别为 `40.831 秒` 和 `39.796 秒`；
    后一次自动 incumbent `17.890 秒`、定价 `12.158 秒`、整数复核
    `9.731 秒`；
  - 定价终止状态为 `TIME_LIMIT`，精确整数结果由自动 incumbent
    保底，不得表述为全宇宙定价已收敛。
- DJX188 生产受控 800 骨架池：
  - 根 LP 在 10 秒内降到约 `17.78` 组的连续下界；
  - 当前默认复跑产生 4,660 个历史与 completion 组列，10 秒精确
    复核状态为 `NOT_SOLVED`，保留 31 组 incumbent，总算法耗时
    `37.142 秒`；
  - 将复核扩大到 30 秒后仍为 `NOT_SOLVED`，总算法耗时约
    `59.8 秒`，结果仍为 31 组。
- automatic22 固定支持仅作为诊断消融，不进入完整搜索：
  - 相同组列主模型得到 `29/1/0`；
  - 当前复跑耗时 `6.767 秒`；
  - 证明主问题与输出语义能表达更好结果，缺口在自动定价生成。
- T42：
  - 自动 incumbent 从 11 组被相同组列流程改善到
    `10 组 / 奇数 1 / 单车 0`；
  - 精确满足 `45 车 / 10,820 mm 废料`；
  - 当前复跑总算法耗时 `11.529 秒`；
  - 无数据集专用花型白名单。

### 15.5 当前结论

“把花型、完整订单配置和连续车数联合定义为列”的建模方向得到验证，
但当前有限 oracle 尚未达到生产验收：

- 连续 LP 下界与整数结果之间存在显著间隙；
- 负 reduced-cost 列能改善 LP，却没有生成足够的联合结构把 DJX188
  从 31 降到目标 29；
- completion 扩充和更长整数预算仍未给出 29 组见证；
- 因此当前代码只能作为研究原型，不能接入生产。

下一步若继续，不应再扩大 7717 全扫描或增加后处理，而应改造定价子问题，
使它直接生成“能共同闭合订单残量的列束”，或进入真正具有节点级定价的
branch-and-price；在达到 `DJX188 <=29/1/0` 前，生产接入门禁保持关闭。
