# T9 关键花型选择审计设计

## 1. 背景与已知事实

上一轮 T9 双池候选逐列审计已确认，人工 65 列中仅 5 列命中 broad 池，rawDeep 精确命中为 0。其余 60 列的首损阶段为：

- `KEY_PATTERN_NOT_SELECTED`：31 列；
- `COMPLETION_CAR_COUNT_PRUNED`：13 列；
- `COMPLETION_LOCAL_CONFIGURATION_PRUNED`：16 列；
- Beam 裁剪：0 列。

本轮只分析占比最大的 31 列，回答它们对应的花型为什么没有进入当前 Top 60 关键花型。当前生产链的真实选择逻辑位于 `OrderGroupIntegerCandidatePoolBuilder.identifyKeyPatterns`：先按残差宽度和残差废边筛出 eligible 花型，再按 LP activity、残差稀缺度、覆盖残差订单数及废边匹配度排序，稳定截取最多 60 个花型。

## 2. 目标

建立“人工 31 列 → 目标花型 → eligible 判定 → 全量评分 → 稳定排名 → Top 60 选择结果”的完整证据链，并回答：

1. 31 列实际涉及多少种不同花型，每种花型在人工 31 列和人工 65 列中分别出现几次；
2. 目标花型是被 eligible 前置条件排除，还是进入候选后排在 Top 60 之外；
3. 排名落后主要来自哪个现有评分分量；
4. 将截断位置离线扩展到 Top 90 或 Top 120 时，目标花型覆盖率如何变化；
5. 下一轮应验证“关键花型数量不足”“评分几何不匹配”还是“残差 eligible 门禁不匹配”。

## 3. 非目标与不可改变项

本轮不做以下工作：

- 不修改 `MAX_KEY_PATTERNS = 60`；
- 不修改关键花型评分公式、排序规则、Packing、候选池规模或时间预算；
- 不把人工 31/65 列的花型签名、频率或其他特征注入生产选择；
- 不运行 Top 90/Top 120 的生产 Packing；离线 Top K 只用于覆盖率诊断；
- 不处理另外 13 列车数候选缺失和 16 列局部配置缺失；
- 不在本轮根据审计结果直接实现算法修复。

## 4. 方案比较

### 方案 A：在真实选择链上采集不可变排名快照（采用）

在 `identifyKeyPatterns` 执行现有 eligible、打分、排序和 Top 60 截断时，通过显式 opt-in 审计入口复制一份不可变快照。生产结果仍由原有对象和原有排序产生；审计数据只旁路读取。

优点：复用真实公式与稳定排序，能覆盖全部竞争花型，不存在测试侧公式漂移；可以直接证明开启和关闭审计时生产签名完全一致。代价：需要给真实链路增加一个默认关闭的观测点。

### 方案 B：在测试代码中重写评分公式（不采用）

测试可读取相同输入后自行重算 eligible、评分和排名。

优点：生产类改动少。缺点：复制了算法逻辑，后续任一公式或 tie-breaker 改动都会使审计存在悄然失真的风险，无法满足“审计真实链路”的证据要求。

### 方案 C：只用上一轮 CSV 离线推算（不采用）

直接基于人工 65 列去向表统计目标花型。

优点：无需代码改动。缺点：上一轮 CSV 没有全部 eligible 竞争花型、评分分量和完整排名，无法解释 Top 60 为什么排除了目标花型。

## 5. 审计链路设计

### 5.1 快照时机

快照必须发生在当前 `identifyKeyPatterns` 内部完成全量打分与稳定排序之后、截取 Top 60 的同一调用中。不得用第二次独立计算替代。

审计开关默认关闭。关闭时不创建排名明细，不写文件，也不改变当前返回列表。开启时仅把本次调用的残差上下文、eligible 判定、评分分量和排序结果交给测试侧收集器。

### 5.2 排名先算、人工信息后关联

生产排名必须先完全计算。人工 31/65 列信息只能在快照形成后按 `patternSignature` 关联，用于增加诊断列：

- 人工 31 列使用次数；
- 人工 65 列使用次数；
- 人工列的 `cars` 分布；
- 人工列的 odd、one-car 数量；
- 人工列订单覆盖摘要。

这些字段不得进入 eligible 判定、评分、排序或 Top 60 截断。`GroupColumn` 只有单一 `cars` 数量，本审计不构造不存在的“车数向量”。

### 5.3 每个全量花型的记录字段

CSV 每行对应一个当前 universe 中的花型，至少记录：

| 字段 | 含义 |
|---|---|
| `patternSignature` | 稳定花型签名 |
| `patternReadable` | 可读花型内容 |
| `eligible` | 是否进入本次评分集合 |
| `ineligibleReason` | `MISSING_RESIDUAL_WIDTH`、`WASTE_EXCEEDS_RESIDUAL` 或其他明确原因 |
| `rank` | eligible 集合内按生产排序得到的 1-based 全局排名 |
| `selectedTop60` | 是否被当前生产 Top 60 选中 |
| `lpActivity` | 当前公式中的 LP 活跃度 |
| `residualScarcity` | 当前公式中的残差稀缺度 |
| `coveredResidualOrders` | 当前花型覆盖的残差订单项数 |
| `wastePerCar` | 花型单车真实废边 |
| `targetResidualWastePerCar` | 当前残差目标单车废边 |
| `wasteFit` | 当前公式中的废边匹配度 |
| `totalScore` | 当前生产公式总分 |
| `widths` | 花型包含的宽度集合 |
| `stationCount` | `pattern.getPattern().values()` 的总和，即花型总刀位数 |
| `distinctWidthCount` | 不同宽度数量 |
| `manual31ColumnCount` | 人工 31 列中使用该花型的次数 |
| `manual65PatternCount` | 人工 65 列中使用该花型的次数 |
| `manualCarsDistribution` | 关联人工列的单一 `cars` 值分布 |
| `manualOddCount` | 关联人工列中 odd 列数量 |
| `manualOneCarCount` | 关联人工列中 one-car 列数量 |
| `manualOrderCoverageSummary` | 关联人工列的订单覆盖数量摘要 |

对 ineligible 花型，`rank` 和各评分字段保持空值；必须输出具体前置过滤原因。若一个花型同时违反多个门禁，记录全部原因，避免由检查顺序掩盖真实问题。

## 6. 统计输出

Markdown 报告至少包含：

1. 31 列对应的不同目标花型数及每花型使用频率；
2. 目标花型排名分桶：`1-60`、`61-90`、`91-120`、`121-300`、`>300`、`INELIGIBLE`；
3. ineligible 原因分布：缺少残差宽度、花型废边超过残差及其他原因；
4. 当前 Top 60、离线 Top 90、离线 Top 120 对目标花型与目标列的累计覆盖数；
5. 目标花型与当前 Top 60 在四个评分分量上的分布对比；
6. 全量排名指纹、残差输入指纹及两次运行一致性结论；
7. CSV 前 20 行预览和完整 CSV 文件链接。

Top 90/Top 120 仅对同一次真实排名快照改变离线截断位置，不重新打分、不生成深池、不运行 Packing。

## 7. 结论分类与下一步边界

审计按下列证据分类，不在同一改动中修复：

### A. 数量截断证据

目标花型集中在少量花型，且多数排名在 61-120。下一步只设计一次“关键花型上限”单变量实验，比较 60、90、120；是否运行 Packing 需另行确认。

### B. 评分几何不匹配

目标花型分散且名次多数在 121 以后，或现有分量系统性把目标花型压到后部。下一步进入评分特征审计，不能把人工频率直接作为生产分数。

### C. 残差 eligible 门禁不匹配

目标花型主要为 ineligible，且集中在缺少残差宽度或废边门禁。下一步审计首次 Packing 残差是否能代表最终组合所需的“胶水花型”，而不是扩大 Top K。

若结果混合，按目标列损失数占比报告主因和次因，不以单个样本强行归类。

## 8. 可复现性与验真

使用与上一轮 T9 双池去向审计相同的数据、参数和人工 65 列 oracle，连续运行两次。每次记录：

- 残差需求、残差车数、残差废边组成的输入指纹；
- universe 及完整稳定排名组成的排名指纹；
- 31 列目标集合指纹；
- Top 60 签名集合；
- 各排名分桶和过滤原因统计。

两次运行必须满足：残差指纹、完整排名指纹、Top 60 签名和统计摘要完全一致；不一致则先报告非确定性来源，本轮不得得出 A/B/C 结论。

测试契约：

1. 审计关闭与开启时，返回的关键花型签名及顺序完全一致；
2. 审计关闭与开启时，后续生产候选签名完全一致；
3. 审计快照 Top 60 与真实返回 Top 60 完全一致；
4. 审计实现中不存在人工花型签名影响 eligible、评分或排序的入口；
5. 报告 Maven/JUnit 实际执行数、成功数和失败数，`0 tests found` 或跳过测试不算通过。
