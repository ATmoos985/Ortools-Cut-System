# 单一质量模式 120 秒可交付版设计

## 1. 目标

对外只保留一个质量求解模式。内部允许分阶段生成和改进 incumbent，但不再向用户暴露“快解”和
“质量解”两个产品档位。

为保持现有调用方兼容，第一版不删除 `qualityMode` DTO 字段；NewSolver 入口统一按质量模式执行，
调用方传入 `false` 不再切回旧快路径。后续 APS 迁移可直接删除该兼容字段。

第一版验收目标：

- sixian 达到或优于 `42/2/0/11`；
- 保持 `cars=462 / waste=102240 / over=0`，逐 `(width|message)` 需求精确守恒；
- 端到端目标耗时不超过 `120000ms`；
- 到达 deadline 时返回已经验收的最好可行 incumbent，不因后续阶段超时丢失结果；
- 不使用数据集名称、固定编号、固定宽度或固定花型作为求解规则。

这里的“精确”首先指业务需求、车数、废边、超产和最终指令完全守恒。只有完整列空间且整数模型
`gap=0` 时才能声明数学全局最优；第一版不作该承诺。

## 2. 当前证据

2026-07-14 当前提交 `bf22b8f` 的 sixian 质量基线为：

- 最终 `42/2/0/11`，`462` 车，废边 `102240`，零超产；
- 端到端 `201.428s`；
- A 层生成两个唯一候选；
- p0 候选：Stage5 为 55 组，双 LNS 后 48 组，SPR 后仍 48 组；
- p0p1 候选：Stage5 为 54 组，双 LNS 后 46 组，SPR 后 41 组；
- p0 的双 LNS 约耗时 86 秒，却不是最终赢家；
- p0p1 的双 LNS 约 46 秒，SPR 约 37 秒，是质量结果的必要路径。

当前根因是候选编排：每个 A 层候选都串行获得完整 Stage5、双 LNS 和 SPR 预算，`timeoutMs` 只是
多个子求解器的局部上限，并非请求级总 deadline。

## 3. 方案比较

### 方案 A：等比例缩短每个阶段

实现简单，但会同时截断赢家 p0p1 的 LNS 和 SPR，较可能丢失 `42/2/0/11`，不采用。

### 方案 B：Stage5 预筛选后只深搜第一名

所有 A 层候选先完成成本较低且业务精确的 Stage5，按真实
`groups -> odd -> one -> small` 排名。只有第一名进入完整 LNS、odd repair 和 SPR；其余 Stage5
结果作为可行 fallback 保留。该方案预计可删除落选 p0 的约 90 秒无收益深搜，本轮采用。

### 方案 C：所有候选并行深搜

墙钟可能下降，但会与 LNS/SPR 内部并行争抢 CPU 和内存，跨机器稳定性差，不适合作为可分发第一版。

## 4. 单一渐进式数据流

`PatternGenerator -> ColumnGeneration -> A层候选 -> Stage5预筛选 -> 第一名质量续跑 -> 全局择优`

具体流程：

1. 保留当前 A 层 parity 候选生成和签名去重，避免删除已验证的候选覆盖。
2. 每个唯一 A 层候选只运行 Stage5 与现有非优化重建，得到合法指令和真实四项指标。
3. 按当前业务字典序稳定排序 Stage5 候选，签名和原 candidate index 作为稳定 tie-break。
4. 将所有 Stage5 结果放入 incumbent 集合，确保后续任何超时都有合法结果。
5. 只对排名第一的 Stage5 候选运行质量续跑：默认 LNS、扩大 LNS、odd repair、SPR。
6. 每接受一次改善就更新 incumbent；候选必须重新通过需求、车数、废边和真实组指标验收。
7. 到达请求级 deadline 后停止启动新阶段，返回当前最好 incumbent。

第一版不自动把 DemandPeakFastStage 插入质量续跑。它已证明能加速普通链，但尚未证明能保持
`42/2/0/11`，且会占用约 5 秒预算。代码继续保留，后续通过相同基准门禁再决定是否纳入质量链。

## 5. 120 秒 deadline

- 质量模式默认总预算 `120000ms`，允许通过请求或运行属性显式覆盖。
- 请求开始时只计算一次绝对 deadline。
- A 层候选循环、Stage5 筛选、LNS 外层迭代和 SPR 都读取同一 deadline。
- 子 SCIP 的 time limit 必须取“本阶段上限”和“请求剩余时间”的较小值。
- 剩余时间不足以安全启动阶段时，直接保留 incumbent，不把 `NOT_SOLVED` 当成不可行。
- 普通异常、超时、重建失败或守恒失败均回退到最近一次已验收 incumbent。

120 秒是正常目标而不是硬杀 JVM 的外部中断。原生 SCIP 调用必须有剩余时间上限；若底层无法及时
响应 interrupt，报告中明确记录实际超时，不伪造达标。

## 6. 修改范围

允许修改：

- `CuttingSolver` 的候选筛选、续跑与 incumbent 编排；
- `InstructionConverter` 的 Stage5 准备和质量续跑边界；
- `SolverRuntimeProperties` 或等价的小型 deadline helper；
- LNS、SPR、Assignment MIP 对请求剩余时间的读取和安全停止；
- `OptimizationExecutionService` 的单一质量配置；
- 直接相关测试、求解报告字段、release 说明和打包产物。

不修改：

- 需求、车数、废边、超产及字典序业务口径；
- 导入导出、数据库、API DTO 字段和前端页面结构；
- PatternGenerator、ColumnGeneration 的数学含义；
- OR-Tools 版本、Maven 构建配置和 CP-SAT 支线。

## 7. 验证与交付

自动测试必须覆盖：

- 多个 A 层候选先 Stage5 排名，只有第一名进入质量续跑；
- Stage5 fallback 在续跑超时、异常或无改善时仍被返回；
- deadline 逐阶段递减，禁止每个子阶段重新获得 120 秒；
- 排名和 tie-break 稳定；
- 需求、车数、废边或指标退化时拒绝候选；
- 普通入口和小数据集不因单一质量编排失效。

真实验证：

- sixian 至少运行 3 次，结果每次不劣于 `42/2/0/11`，中位数不超过 120 秒；
- T42 结果不劣于当前质量基线；
- t9 在可承受预算内验证可行返回、守恒和实际耗时，不用单次结果宣称普遍最优；
- 报告实际执行测试数、成功数、失败数、错误数和跳过数。

交付物：中文 Git 提交、经过检查的 runnable jar、现有 release 目录必需文件、带时间戳 zip，以及一份
说明版本、配置、已验证数据和当前最优性边界的 release 文本。
