# 两步式统一切割求解器设计

## 1. 结论

目标架构不是“把 SCIP 换成 CP-SAT”，而是把当前分散在 Stage4、Stage5、LNS 和 SPR
中的执行结构优化收敛为两步：

1. 生成订单感知的可执行列。
2. 在固定车数和废边边界下执行统一 set-partition，并按
   `序号组 -> 奇数车组 -> 小车数组` 严格字典序优化。

仓库现有 `UnifiedSetPartitionSolver` 已经具备统一主问题的基本数据结构和守恒约束，
本方案在该实现上演进，不创建第二套互不兼容的统一模型。CP-SAT 只作为确定性后端候选；
在兼容性、质量和耗时验收完成前，生产链路保持不变。

## 2. 当前事实

当前生产链路为：

`PatternCandidate -> Stage4 -> Stage5 -> LNS -> SPR -> InstructionConverter`

各阶段职责如下：

| 阶段 | 当前职责 | 两步架构中的去向 |
| --- | --- | --- |
| PatternGenerator/ColumnGeneration | 生成宽度花型 | 保留，作为可执行列形状来源 |
| Stage4 | 选择花型及使用次数 | 最终由统一主问题覆盖 |
| Stage5 | 把花型分配到具体订单消息 | 前移到可执行列生成 |
| LNS | 局部重排订单块 | 作为研究期列发现器，稳定后可删除 |
| SPR | 残差微邻域 set-partition | 能力合并到统一主问题，保留为列发现器 |
| InstructionConverter | 验收、排序、输出 | 保留非优化部分 |

`UnifiedSetPartitionSolver.Column` 已包含：

- `pattern`：宽度到条数。
- `config`：宽度到每个工位的订单消息文本。
- `patternWidth`：单车搭切宽度。
- `demandUse()`：该列每车对 `(width|message)` 需求的消耗。

现有统一主问题已经约束：

- `(width|message)` 需求精确覆盖。
- 总车数精确等于已知最优车数。
- 总废边不超过已知最优废边。
- 每种可执行列的使用次数和启用状态联动。

当前主要缺口是：

1. 可执行列池不是完整枚举，只能证明“当前列池内最优”。
2. 当前目标只完整表达了组数和 odd，small 只统计、未进入严格第三阶段目标。
3. SCIP 墙钟/节点截断下的可行解仍可能摇摆。
4. 统一模型尚未形成生产解到 `CuttingInstruction` 的独立、可验收适配边界。

## 3. 方案比较

### 方案 A：只用 CP-SAT 替换 Stage4

优点是改动小，可以优先解决 Stage4 花型签名摇摆。缺点是 Stage5、LNS、SPR 仍然存在，
不能形成两步架构，也不能直接优化真实序号组。

该方案只作为 OR-Tools 9.15 兼容性和确定性验证入口，不作为最终架构。

### 方案 B：演进现有统一 set-partition，推荐

保留现有花型生成器，把 Stage5、LNS 和 SPR 已发现的订单配置规范化为可执行列，统一求解后
通过适配器输出指令。先证明列池内最优，再扩展列发现覆盖率。

优点是复用已验证模型、改动可分阶段回退、能直接优化业务指标。缺点是列池完整性仍需长期研究。

### 方案 C：一次性全局枚举并重写

直接枚举全部“花型 x 消息分配 x 块大小”并交给 CP-SAT。理论边界最完整，但列空间会快速爆炸，
且当前 Windows Java 原生运行时尚未通过 CP-SAT 冒烟，因此本阶段不采用。

## 4. 目标架构

### 4.1 第一步：可执行列生成

新增清晰的列归档边界，输入为花型池、订单需求和已有可行解，输出为按签名排序去重的
`ExecutableColumnPool`。列来源分层记录：

1. `PIPELINE`：当前 Stage5/LNS/SPR 可行解中的全部列，保证 warm start 可重建。
2. `STRUCTURED`：现有 `structuredColumns()` 从花型和消息需求生成的结构化列。
3. `RESIDUAL`：SPR 残差导向产生的列。
4. `ENUMERATED`：受控完整枚举产生的列，仅研究模式启用。

列签名必须稳定，并至少覆盖：

- 排序后的宽度及工位消息文本。
- 单车搭切宽度。
- 每个 `(width|message)` 的消耗量。
- 来源和首次发现轮次作为元数据，不进入等价性签名。

列池必须先做支持度过滤：任何需求键单车消耗超过总需求的列不得进入主问题。

### 4.2 第二步：统一字典序主问题

对每列 `j` 定义：

- `c_j`：该可执行列使用车数。
- `y_j`：是否启用，`c_j > 0`。
- `o_j`：`c_j` 是否为奇数。
- `s_j`：是否为小车数组，定义为 `1 <= c_j <= 5`。

硬约束：

1. 每个 `(width|message)` 精确覆盖。
2. `sum(c_j) = exactCars`。
3. `sum(waste_j * c_j) <= wasteCap`。
4. `c_j` 与 `y_j/o_j/s_j` 正确联动。

严格分三次求解：

1. 最小化 `sum(y_j)`，得到 `bestGroups`。
2. 固定 `sum(y_j) <= bestGroups`，最小化 `sum(o_j)`，得到 `bestOdd`。
3. 固定组数和 odd 上限，最小化 `sum(s_j)`。

不使用小数权重模拟字典序，避免列数变化导致权重失效。

### 4.3 后端边界

统一主问题通过内部后端接口隔离：

- `SCIP`：保留现有实现和生产回退能力。
- `CP_SAT_RESEARCH`：仅 OR-Tools 9.15 冒烟通过后启用，固定单线程、变量顺序、随机种子和
  `deterministic_time`，墙钟只作安全帽。

两个后端必须返回统一诊断：状态、目标、best bound、gap、节点或分支数、确定性时间、墙钟时间、
列池签名和结果签名。

## 5. 输出与验收边界

统一结果先转换为 `AssignmentBlock`，再复用 `InstructionConverter` 的非优化构建、排序和导出逻辑。
转换后执行独立验收：

- `(width|message)` 需求完全一致。
- 车数完全一致。
- 废边不增加。
- 组数、odd、small 与模型结果一致。
- 工位数量和花型宽度一致。

验收失败时研究结果作废，生产结果不受影响。

## 6. 删除机制的门槛

本阶段不删除 Stage4、Stage5、LNS 或 SPR。只有统一模型同时满足以下条件，才允许逐项删除：

1. sixian 连续 5 次不差于 `42/2/12`。
2. t9est188 连续 5 次不差于 `66/8/26`。
3. 总车数、废边和需求守恒每次一致或更优。
4. P95 不超过 sixian 5 分钟、t9est188 12 分钟。
5. 结果签名稳定；时间变异系数不超过 15%。
6. 新模型可通过 warm start 重建旧模型的已知最好解。
7. 快速解路径不受影响。

删除顺序为：

1. 先删除被统一主问题覆盖的 LNS 双变体。
2. 再删除 SPR 后处理，但保留其残差列生成器。
3. 再将 Stage5 收缩为输出适配器。
4. 最后评估是否取消 Stage4 独立花型选择。

## 7. 验证计划

### 7.1 OR-Tools 9.15 兼容性门

1. 默认依赖仍为 9.10，通过 Maven 属性允许实验覆盖到 9.15.6755。
2. 9.15 下运行最小 CP-SAT 布尔模型，必须返回 OPTIMAL，禁止 JVM 原生崩溃。
3. 9.15 下运行全部非长耗时回归并报告实际测试数。
4. 检查 SCIP 参数、结果和原生库加载是否兼容。

### 7.2 模型正确性

1. 单列精确覆盖。
2. 多个等价最优解时按 `组 -> odd -> small` 选择。
3. 不可满足的车数、废边或需求返回明确不可行状态。
4. warm start 列必须能被完整匹配。
5. 相同列池重复求解的结果签名一致。

### 7.3 业务基准

先运行现有 `B6UnifiedSetPartitionTest` 的小层级，再执行：

- sixian 影子求解 3 次。
- t9est188 影子求解 3 次。
- 最终候选各 5 次，统计 P50、P95、最小值、最大值和变异系数。

报告必须明确区分：可行上界、列池内最优、原问题全局最优。

## 8. 本阶段交付

1. OR-Tools 9.15 隔离冒烟与兼容性结论。
2. 可执行列池及结果签名的稳定契约。
3. 严格三级字典序统一主问题研究实现。
4. 小模型和现有 B6 层级验证。
5. sixian/t9est188 影子结果；未达门槛时不接入生产。
