# DJX188 支持生成平台化探针设计

## 1. 背景与当前证据

当前唯一有效的候选基线是
`djx188-support-candidate-snapshot-v1.tsv`，其载荷哈希为
`52ebe9a752b827cd3cea64a7da70cb042224ce8f7a6652c8f73a0af1a7f671e3`，
包含 316 个状态和 26 个支持结构。旧的 232 状态/17 支持结果只保留为历史参考，
不得与当前基线合并计算覆盖率。

当前基线已完成每个支持 Top-1/2/3 的精确复核：78/78 均不能达到
`groups <= 27, oddGroups = 1, oneGroups = 0`，且未观察到目标可行性或精确组数反转。
这说明评价链路在已检查范围内稳定，但不能证明剩余 238 个状态或完整生成空间不存在目标解。

生成侧曾在相同量级的 20 秒/层预算下得到 17、24、26 个支持。该轨迹只能证明存在漂移，
不能说明生成仍在持续增长，也不能说明已经平台化。下一步必须把“相同预算下的运行间方差”
和“预算增加后的边际新增支持”分开测量。

## 2. 目标

本轮只回答一个问题：

> 在固定 DJX188 数据、三层局部宇宙、SCIP 参数和容量上限下，支持生成在
> 20/60/180 秒预算上是否呈现经验平台？

具体目标：

1. 测量 20 秒/层相同配置下的运行间漂移；
2. 测量预算从 20 秒增加到 60 秒、180 秒时的边际新增支持；
3. 将每次运行的支持集合、状态集合、层级指标、配置身份和统计摘要持久化；
4. 与固定 316/26 快照比较交集、缺失、新增和 Jaccard 重叠率；
5. 根据真实终止状态给出 `STILL_GROWING / EMPIRICAL_PLATEAU / PROVEN_EXHAUSTED / INCONCLUSIVE`
   之一，不把单次观测或超时误写成数学穷尽；
6. 用结果决定下一阶段是深挖固定池 Top-N，还是先扩大生成预算并建立新候选基线。

## 3. 方案比较

### 3.1 单次预算阶梯

每档只运行一次 20/60/180 秒。总耗时最低，但无法区分预算效应和单次墙钟波动，
只能形成弱证据，不采用。

### 3.2 混合重复预算阶梯（采用）

- 20 秒/层运行 3 次；
- 60 秒/层运行 2 次；
- 180 秒/层运行 2 次。

共 7 次三层生成，预计求解时间约 27 分钟。该方案保留 20 秒档较充分的方差估计，
同时让 60、180 秒档不再是单点观测，是统计强度与工程成本之间的折中。

### 3.3 每档运行 3 次

统计对称性最好，但预计求解时间约 39 分钟。本轮先不采用；如果 60/180 秒两次结果差异明显，
后续只补对应预算档的第 3 次，而不重跑全部实验。

## 4. 范围与非目标

本轮允许：

- 新增研究侧平台化探针、归档器和单元测试；
- 读取现有 316/26 快照作为固定比较基线；
- 运行现有三层局部宇宙和稀疏生产中性支持生成；
- 创建独立的平台化结果文件并原子回读校验；
- 提交测试代码、设计文档和真实探针结果。

本轮禁止：

- 修改生产代码；
- 修改三层局部宇宙构造规则；
- 修改稀疏 MIP 目标函数、约束或排序；
- 启用二跳桥接；
- 运行 Phase2、Stage5 或 order-compatibility 精确核；
- 修改、覆盖或重新生成现有 316/26 候选快照及其精确结果侧车；
- 把不同运行的状态数或支持数简单相加；
- 把超时、到达容量上限或经验稳定宣称为全局穷尽。

## 5. 固定实验配置

所有运行共享：

- DJX188 需求与 automatic22 基线；
- 7717 个完整花型宇宙；
- WITNESS_DIRECT 121 个花型；
- NEUTRAL_CLOSURE 370 个花型；
- TRANSFER_BRIDGE_1_HOP 1050 个花型；
- `sparseSupportMs=15000`；
- `sparseNodeLimit=200000`；
- `sparseMaxSupports=200`；
- `sparseMaxCoefficients=2000`；
- `sparseMaxStates=500`；
- SCIP 单线程；
- `randomseedshift=0`；
- `permutationseed=0`；
- `lpseed=0`；
- 169 车、36870 废料和逐宽幅精确产需不变量。

预算档只改变：

- `sparseTotalMs`；
- `sparseMasterMs`。

两者在每档均取 20000、60000 或 180000 毫秒。每一层分别获得该预算，
不是三层共享一个总预算。

## 6. 数据流

```text
读取固定 316/26 快照并校验哈希
  -> 加载 DJX188、automatic22 与 7717 完整宇宙
  -> 精确重建 121/370/1050 三层局部宇宙
  -> 构造单位 2 换 2 排除状态及兼容性见证优先集合
  -> 按 20x3、60x2、180x2 依次运行三层稀疏支持搜索
  -> 每次运行只冻结生成状态与支持身份
  -> 计算运行内、同预算档、跨预算档和固定基线重叠指标
  -> 构造平台判定
  -> 写入临时文件
  -> 完整回读、哈希和统计重算校验
  -> 原子创建正式结果文件
```

探针不得调用 `ProductionNeutralMoveSearch.fastUpperBound`、
`OrderCompatibilityKernelAnalyzer.checkThreshold/analyze` 或任何生产 Stage5 入口。

## 7. 持久化格式

新增研究格式：

```text
support-generation-plateau-v1
```

建议路径：

```text
src/test/resources/research-baselines/
  djx188-support-generation-plateau-v1.tsv
```

### 7.1 文件身份

头部至少记录：

- 格式版本、数据集和创建时间；
- 固定候选快照载荷哈希；
- 需求、automatic22、完整宇宙和三层宇宙哈希；
- 完整生成配置哈希；
- Java、OR-Tools、SCIP、线程和随机种子；
- 预算重复计划 `20000x3,60000x2,180000x2`；
- 运行数、支持记录数、状态记录数；
- 规范化载荷 SHA-256。

易变生产信息不参与规范化载荷哈希；配置、运行指标和实际集合必须参与。

### 7.2 每次运行

每个运行记录：

- 预算、重复序号和稳定 run id；
- 每层状态、支持、主求解次数、系数解数、节点数、耗时和终止状态；
- 每层是否穷尽、超时或到达数量上限；
- 合并后的唯一状态数和支持数；
- 与固定 316/26 基线的交集、仅探针、仅基线和 Jaccard；
- 全部合并支持身份；
- 全部合并状态签名。

支持身份和状态签名按字典序写入并使用安全编码，确保结果可独立重算，
不能只保存聚合数字。

### 7.3 统计摘要

每个预算档分别报告：

- 支持数和状态数的最小值、最大值、均值、中位数；
- 支持数和状态数的样本标准差；
- 同预算运行两两 Jaccard 的最小值、最大值和均值；
- 所有重复的支持交集（稳定核心）和并集；
- 各次运行与固定 26 支持的重叠分布。

跨预算报告：

- `union60 - union20`；
- `union180 - union(20,60)`；
- 每档新增支持的完整身份列表；
- 三档累计支持并集；
- 60/180 档内部重复结果是否存在明显漂移。

不把上述多维指标压缩成单一“置信度百分比”。

## 8. 平台判定语义

判定按 `PROVEN_EXHAUSTED -> STILL_GROWING -> EMPIRICAL_PLATEAU -> INCONCLUSIVE`
的证据优先级执行。60 秒和 180 秒档的“内部稳定”统一定义为：同档两次运行的支持集合
Jaccard 不低于 0.90，且支持数相对极差 `(max-min)/max` 不超过 0.10。

### 8.1 `PROVEN_EXHAUSTED`

只有 180 秒档两次运行中的三个层级全部明确返回穷尽、两次合并支持集合一致，
且相对低预算累计并集没有新增支持时才能使用。
该结论仍只针对固定三层局部宇宙和当前移动定义，不代表 7717 全局零空间穷尽。

### 8.2 `STILL_GROWING`

180 秒档出现不属于全部 20/60 秒运行并集的新支持时使用。若同时触发容量上限，
仍判为 `STILL_GROWING`，并额外报告容量边界。
此时优先扩大或重构生成，不深挖当前 316 状态。

### 8.3 `EMPIRICAL_PLATEAU`

180 秒两次运行均未产生超出 20/60 秒累计并集的新支持，60/180 档均满足上述内部稳定阈值，
没有触发支持、系数或状态容量上限，但生成器仍因时间停止、没有给出穷尽证明时使用。
该结论必须显式标注“经验平台、非数学穷尽”。

### 8.4 `INCONCLUSIVE`

以下任一情况成立时使用：

- 60 或 180 秒档的 Jaccard 低于 0.90，或支持数相对极差超过 0.10；
- 未观察到 180 秒新增支持，但到达支持、系数或状态容量上限；
- 某次运行异常退出或集合证据不完整；
- 单次结果不足以区分预算增长和正常波动。

若 60 或 180 秒两次结果差异明显，下一步只补该预算档第 3 次运行，
不直接宣布平台，也不立即扩大 Top-N。

## 9. 组件设计

### 9.1 `SupportGenerationPlateauArchive`

职责：

- 定义 v1 记录模型；
- 规范化编码、载荷哈希与回读校验；
- 从持久化支持集合重算全部统计摘要；
- 使用临时文件和原子移动创建结果；
- 默认拒绝覆盖已有结果；
- 不调用任何求解器。

### 9.2 `Djx188SupportGenerationPlateauExperimentTest`

职责：

- 复用现有 DJX188 fixture 和三层构造链路；
- 读取并锁定固定 316/26 快照；
- 按预算计划生成 7 个独立运行；
- 明确打印 `phase2Invoked=false`、`exactInvoked=false`、`snapshotModified=false`；
- 创建平台化结果并立即回读；
- 输出每档统计和最终判定。

### 9.3 不修改现有快照实验

`Djx188SupportCandidateSnapshotExperimentTest` 继续只负责 316/26 快照及 Top-N 精确侧车。
平台化探针不在其中增加 `PROBE` 或隐式覆盖模式，避免两个证据文件生命周期耦合。

## 10. 测试与验证

### 10.1 归档器单元测试

- 相同集合不同输入顺序得到相同载荷哈希；
- 写入后可完整回读并重算统计；
- 修改任一支持身份、状态签名、预算或终止状态后校验失败；
- 固定快照哈希不一致时拒绝读取；
- CREATE 不覆盖已有文件；
- 统计中的交集、并集、差集和 Jaccard 与手工小样本一致；
- 四种平台判定状态均有独立测试。

### 10.2 默认测试行为

真实探针必须由系统属性显式开启；普通测试运行时只跳过，不消耗长求解预算。
报告必须区分实际成功、失败和按设计跳过的测试数。

### 10.3 真实实验验收

- 实际生成 7 次三层运行；
- 每档重复次数与计划一致；
- 三层花型数仍为 121/370/1050；
- 固定基线仍为原哈希、316 状态、26 支持；
- Phase2 和精确核调用次数均为 0；
- 结果文件写入后回读哈希一致；
- 再次使用 REPLAY/VERIFY 模式时不调用生成器；
- 现有快照和精确侧车在实验前后文件哈希完全一致；
- 如实报告每次运行及最终判定，不预设一定平台化。

## 12. 完成后的路线决策

- `STILL_GROWING`：暂停 Top-5，优先研究更大预算、目标信号或生成范围；
- `EMPIRICAL_PLATEAU`：保留“非穷尽”边界，继续当前 316 状态的 Top-5/Top-10；
- `PROVEN_EXHAUSTED`：在固定局部宇宙内继续深挖或评估二跳扩展；
- `INCONCLUSIVE`：先补差异明显预算档的第 3 次重复，不改变候选基线。

无论结果如何，本轮都不自动创建新候选快照；建立新基线必须经过独立确认。
